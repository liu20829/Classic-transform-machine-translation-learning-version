# 数据集体检与真实规模

> 一句话：采样 20 万行把语料的句长、丢弃率、词频分布全部量出来，结论是"数据不是不够，是只用了 4%"——顺手也验证了 `max_sent_len=50` 这个看似武断的值其实选得很准。
> 关键词：WMT zh-en, 句长分布, 丢弃率, Zipf, min_count, UNK 率, token 计数
> 生成日期：2026-09-30
> 上游问题：①「我这个数据集的体量，当前的训练参数你感觉可以吗？」
> 下游文档：[参数量与过拟合的真实来源](./调参经验-参数量与过拟合的真实来源.md)（本篇量出的 token 数是那篇算比值的分母）

## 起点：为什么不能凭感觉回答"参数行不行"

当时的处境是：`max_pairs=1000000`、词表 zh 181564 / en 119110、模型 256 维 7+7 层，train acc 43.7% vs valid acc 33.7%，明显过拟合。直觉上的应对是"调 dropout / 缩模型 / 加正则"。

但这个判断缺一个前提：**这 100 万对到底是多少 token？模型又是多少参数？** 没有这两个数，"过拟合"只能定性不能定量，也就没法知道该往哪个方向使劲。

所以第一步不是调参，是把数据量出来。

## 一、数据在哪、怎么量

语料在仓库里，不需要上服务器：

```
my_data/WMT_dataset/wmt_zh_en_training_corpus.csv    6,359,269,704 字节 ≈ 6.36 GB
```

| 项 | 值 | 来源 |
|---|---|---|
| 全语料行数 | 24,752,393 对（约 2475 万） | README（WMT 2021 News Translation Task，ParaCrawl 等合成） |
| CSV 表头 | `['0', '1']`，列 0 = 中文，列 1 = 英文 | 实读 |
| 当前 `max_pairs` | 1,000,000 | 脚本配置 |

**度量方法**：`csv.reader` + `itertools.islice` 顺序读前 **200,000 行**，用列表推导统计句长，用 `collections.Counter` 统计词频。不建完整词表、不做 tokenize，2.5 秒跑完。

> ⚠️ 为什么必须先 `next(reader, None)` 跳表头：首行是列名 `'0','1'`，不是数据。`my_dictionary.load_pairs()` 里就是这么做的。

## 二、句长分布：`max_sent_len=50` 是个好值

句长按"空格切出来的 token 数"算（语料本身已经分好词：`表演 的 明星 是 ...`）：

| | mean | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| 中文 | 20.7 | 20 | 28 | 31 | 38 | 73 |
| 英文 | 22.3 | 22 | 29 | 31 | 37 | 57 |

中文字符数 mean 54.3 / p95 82（一个词平均 2.6 个汉字）。

再看不同阈值下的丢弃率（**任一边超长就整对丢弃**，见 `load_pairs`）：

| `max_sent_len` | 丢弃率 | 保留 |
|---|---|---|
| 30 | 8.87% | 91.13% |
| 40 | 0.66% | 99.34% |
| **50** | **0.03%** | **99.97%** |
| 60 | 0.00% | 100.00% |
| 80 / 100 / 128 | 0.00% | 100.00% |

**结论：50 已经很贴边，别动。** p99 才 38，50 覆盖到 max（中文 73、英文 57）附近，只丢 0.03%。

两个方向都不划算：
- 往上加（60/80）：丢弃率已经是 0，加长度只是徒增序列长度和显存；
- 往下砍（30）：要丢 8.87% 的数据——那是**拿数据换序列长度**，而数据恰恰是这一轮最稀缺的东西。

> 这条纠正了一个常见的直觉："50 是不是截断太狠了？" 数据说话：不狠，实测 99.97% 的句对都在 50 个 token 以内。

## 三、词表与 UNK：`min_count` 的性价比

采样 20 万对统计词频（这会**低估**全量词表，因为低频词还没出现够次数）：

| | min_count=1 | min_count=2 | min_count=3 | min_count=5 |
|---|---|---|---|---|
| 中文词表 | 157,217 | 80,979 | 59,067 | 40,599 |
| 中文 UNK 率 | 0.00% | 1.84% | 2.90% | 4.41% |
| 英文词表 | 104,660 | 57,960 | 44,860 | 33,613 |
| 英文 UNK 率 | 0.00% | 1.05% | 1.63% | 2.49% |

脚本注释里记的实测值（100 万对）：**zh 181564 / en 119110**（min_count=2）。20 万对采样得到的 80979 / 57960 明显更小，这是 Zipf 分布的正常现象——语料越大，能攒够 2 次的低频词越多。

**关键的一步是把词表和"贡献"对照起来看**：

| | 占比 |
|---|---|
| 只出现 1~2 次的词 | 占词表一多半 |
| 它们贡献的 token | **不到 1%** |

**结论：用不到 1% 的覆盖率，养着词表里一大半的参数行。** 这是 `min_count` 2→3 的依据：UNK 率从 1.84%/1.05% 涨到 2.90%/1.63%（多约 1 个点），换来词表规模砍掉约 40%。这笔账的具体收益见 [参数量与过拟合的真实来源](./调参经验-参数量与过拟合的真实来源.md)。

> ⚠️ 不要把"UNK 率"理解成"翻译质量下降 1 个点"。UNK 命中的是极低频词，模型本来就学不好它们；归入 UNK 后至少有一个统一的、能学到东西的符号。

## 四、token 总量：这才是配参的基准单位

每对句子的 token 数（含 SOS/EOS 各 +1）：中文 **22.7**、英文 **24.3**（用 mean 20.7 / 22.3 加 2）。

按 24,752,393 行、保留率 99.97%、训练集占 80% 外推：

| `max_pairs` | 过滤后句对 | 训练集句对 | 训练集中文 token |
|---|---|---|---|
| 200,000 | 20.0 万 | 16.0 万 | **3.6 M** |
| 1,000,000 | 100.0 万 | 80.0 万 | **18.2 M** |
| 2,000,000 | 200.0 万 | 160.0 万 | **36.3 M** |
| 5,000,000 | 500.0 万 | 400.0 万 | **90.8 M** |
| 10,000,000 | 1000.0 万 | 800.0 万 | **181.5 M** |
| 24,752,393（全量） | 2475 万 | 1980 万 | **449.4 M** |

这张表是**整个调参的基准**：token 数才是"数据量"，句对数不是。下一步就是拿它去除参数量。

## 五、每轮步数与时间账

训练集 80%、验证集 20%（`my_dataloader.py` 的 `test_size=0.2` × `0.2`，实际 train:valid:test ≈ 80:16:4）：

| `max_pairs` | train batch（B=128） | valid batch |
|---|---|---|
| 1,000,000 | 6,248 | 1,562 |
| 2,000,000 | 12,496 | 3,124 |
| 5,000,000 | 31,239 | 7,810 |
| 24,752,393 | 154,650 | 38,662 |

> **口径提醒**：历史日志 `第一次训练.txt` 里验证集是 1,250 batch（对应 20 万对？不是——那轮 max_pairs 是 100 万，但 valid 是 1,250 而不是 1,562）。差异来自验证集比例的改动：那轮是 `train_test_split(test_size=0.2)` 直接 80/20，现在是 20% 之后再切 20%，所以 valid 缩小、test 单独分出来。**对照新旧 loss 时要注意验证集不是同一份**。

时间按脚本注释里的实测 `0.087 s/batch`（batch=128，约 1230 样本/s）直推：

| `max_pairs` | 分钟/轮 | 30 轮 | 早停（约 20 轮） |
|---|---|---|---|
| 100 万 | 9.1 | 4.5 h | 3.0 h |
| 200 万 | 18.1 | 9.1 h | 6.0 h |
| 500 万 | 45.3 | 22.6 h | 15.1 h |
| 1000 万 | 90.6 | 45.3 h | 30.2 h |

> ⚠️ 这是**用旧配置（B=128、单进程、fp32）外推**的数字。改成 B=512 + 多进程 + bf16 之后会明显变快，但快多少必须实测——原因见 [显存预算与硬件取舍](./调参经验-显存预算与硬件取舍.md) 里关于"CPU 才是瓶颈"的那一节。

## 六、本篇的结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | 数据体量不是问题：全语料 2475 万对，当前只用 100 万（**4%**） | 24,752,393 vs 1,000,000 |
| 2 | `max_sent_len=50` 选得准，只丢 0.03%，别动 | 丢弃率表 |
| 3 | `min_count=2` 太保守：一半词表行只贡献不到 1% token | 词频分布 |
| 4 | 配参的基准是 **token 数**，不是句对数 | token 总量表 |
| 5 | 该做的实验是"把 `max_pairs` 提上去"，不是调 dropout | 全部上表 |

## 复现这份体检的方法

采样统计的要点（不建词表、不 tokenize，所以很快）：

```python
import csv, itertools, collections
zh_tok = []
zh_counts = collections.Counter()
with open(CSV, encoding='utf-8', newline='') as f:
    r = csv.reader(f)
    next(r, None)                      # 跳表头 '0','1'
    for row in itertools.islice(r, 200_000):
        if len(row) < 2: continue
        zt = row[0].strip().split(' ')
        zh_tok.append(len(zt))
        zh_counts.update(zt)           # 词频：后面按 counts 算 min_count 各档的词表与 UNK 率
```

丢弃率只要两两比较即可：

```python
drop = sum(1 for a, b in zip(zh_tok, en_tok) if a > lim or b > lim) / n
```

> 注意 `load_pairs` 用的是 `len(zh.split(' ')) > max_sent_len`，即**严格大于**才丢。体检脚本要与它保持同一个比较方向，否则算出来的丢弃率会差一档。
