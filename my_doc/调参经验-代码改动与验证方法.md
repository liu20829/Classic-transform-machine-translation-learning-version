# 代码改动与验证方法

> 一句话：本轮落地的是四处改动（断点续跑、weight tying、向量化拼装、混合精度），每一处都配了能自动跑的断言——自检脚本抓出了三个真 bug，其中一个只有跑起来才会暴露。
> 关键词：断点续跑, last.pth, 状态恢复, 原子写, 验证脚本, 冒烟测试
> 生成日期：2026-09-30
> 上游问题：④「把参数写好吧，到时候我直接上传程序运行」
> 上游文档：[显存预算与硬件取舍](./调参经验-显存预算与硬件取舍.md)、[参数量与过拟合的真实来源](./调参经验-参数量与过拟合的真实来源.md)

## 起点：为什么先补断点续跑

在改超参之前先加断点续跑，有一个具体理由：**`results/bleu.txt` 里那轮 BLEU 到 52 个 epoch 还在上升**，而当前配置是"30 轮上限 + 早停 8"——训练被上限截断了。1000 万对一轮接近一小时，如果不支持续跑，"多练几轮"就意味着从头再来。

所以顺序是：**先让训练可以随时停随时接，再调参。**

## 一、断点续跑：要存的是"下一轮从哪继续"

### 1.1 存什么

每个 epoch 跑完覆盖写 `checkpoints/last.pth`：

| 字段 | 不存会怎样 |
|---|---|
| `model_state` | 没法继续 |
| `optimizer_state` | AdamW 的动量、平方梯度归零，loss 有一次小回弹；`param_groups` 里的当前 lr 也在里面 |
| `scheduler_state` | `ReduceLROnPlateau` 的 `best` / `num_bad_epochs` 归零。**`patience=12` 时要重新数 13 轮才可能降 lr**——这是"lr 被砍到 6.25e-6 后空转 60 轮"那类问题的来源 |
| `rng_state`（CPU + CUDA） | `DataLoader(shuffle=True)` 用的是**全局** RNG，不恢复第 N+1 轮的 batch 顺序会重新抽，续跑就不等于"没停过" |
| `best_val_acc` / `best_val_loss` | 存 best 的判据和早停判据都从零开始 |
| `bad_epochs` / `early_stop_patience` | 早停计数归零，白等 8 轮 |
| `scaler_state` | 混合精度的动态损失缩放从初始值重爬，头几步可能白跳一次 |
| `meta`（`batch_size`/词表大小/数据条数） | 续跑时无法核对"是不是同一道题" |

> `scheduler_state` 用 `scheduler.state_dict()`。**注意 `ReduceLROnPlateau` 的 `state_dict()` 在旧版 PyTorch 里不含 `best`/`num_bad_epochs`** —— 那两个正是"连续几轮没提升该砍 lr"的计数器。恢复失败时要打警告而不是静默继续。

### 1.2 三个容易写错的地方

**① 原子写**

```python
tmp = path + '.tmp'
torch.save(ckpt, tmp)
os.replace(tmp, path)        # 同目录 rename 是原子的
```

不这么做的话，写到一半被 kill 会留下半截文件，下次续跑直接报错。**最坏情况应该是"丢当前这一轮"，而不是"档案损坏"。**

**② `weights_only` 的坑（torch 2.6 起默认 True）**

```python
try:
    return torch.load(path, map_location='cpu', weights_only=True)
except Exception:
    return torch.load(path, map_location='cpu', weights_only=False)
```

`meta` 里有 dict 和 str，`weights_only=True` 读不动。优先用安全模式、失败再退回，比一路 `weights_only=False` 好。

**③ 续跑要落回原来的日志目录**

`log_root` 固定成断点所在那一轮的目录，TensorBoard 标量接着写。否则每次续跑都新建一个 `base_trian_log_*`，曲线断成好几张图，看不出趋势。

### 1.3 "存 best 的模型"不等于"能续跑"

这是本轮最值得记的一条。旧脚本 `train_增加学习了自动调整版.py` 存的是：

```python
ckpt = {"epoch":..., "model_state":..., "optimizer_state":..., "val_acc":...}
torch.save(ckpt, os.path.join(CHECKPOINT_DIR, best_name))   # 只在 val_acc 创新高时写
torch.save(ckpt, BEST_MODEL_PATH)
```

| 问题 | 后果 |
|---|---|
| 只在 `valid_acc > best_val_acc` 时写 | acc 横盘或下降的轮次**一个文件都不落** |
| 存的是**历史最优那轮**的模型 | 从它续跑 = 退回最高分的位置，不是断点前最后那轮 |
| 没有 `scheduler_state` / `rng_state` / 早停计数 | 见上表 |
| `LAST_MODEL_PATH` 只被赋值、从没被 `torch.save` 用过 | "每轮存一份"的设计没落地 |

所以旧脚本的产物是**最优模型存档**（够用来推理/微调），不是**训练断点**。两者要分开。

### 1.4 兼容旧断点时的两个陷阱

新脚本能直接吃旧格式断点，但有两处必须处理：

**陷阱一：`best_val_acc` 不能用 0.0 兜底**

旧断点存的是历史最优那轮的模型，它当时的 acc 必然 > 0。如果拿 `0.0` 当"历史最好"，续跑后**每一轮都会判成创新高**——每轮白存一份 best 文件，best 的含义也乱了。正确做法是用 `-inf` 起手，让续跑后第一轮先把真实分数重新记一遍。

同理 `best_val_loss` 用 `inf`：第一轮的 valid loss 一定是"新低"，不会一上来就背着 8 轮的坏计数被判早停。

**陷阱二：配置核对不能被"提前 return"跳过**

```python
# 错：没轮次可跑就直接 return，顺手把配置检查也跳过了
if start_epoch >= epoch:
    return
check_resume_config(...)

# 对：先核对，再判断有没有轮次
mismatch = check_resume_config(saved, config, batch_size)
if mismatch: print("⚠️ 断点与本次配置对不上：" + "，".join(mismatch))
if start_epoch >= epoch: print("没有可跑的轮次")
```

配置换了却因为"没轮次可跑"而一个字不报，是最坑的一种静默错误。

## 二、weight tying

```python
self.linear = nn.Linear(model_dim, y_vocab_size, bias=False)   # bias 必须在这里就写 False
self.linear.weight = self.embedding_positional.embedding.weight  # 指向同一份 Parameter
```

`nn.Linear` 的 bias 是创建时定死的，事后 `del self.linear.bias` 是脏操作（optimizer 里可能还留着引用）。

细节与论证见 [参数量与过拟合的真实来源](./调参经验-参数量与过拟合的真实来源.md)。

> ⚠️ **改 tying 之后不能续跑 tying 之前的断点**：模型参数名变了（`decoder.linear.weight` 消失），`load_state_dict` 会在 unexpected keys 上直接报错。这是**好事**——总比静默丢掉 30.6M 参数强。要换配置就 `--fresh`。

## 三、向量化 batch 拼装

```python
def _to_batch(batch, device):
    src = torch.tensor([e['src'] for e in batch], dtype=torch.int64)
    tgt = torch.tensor([e['tgt'] for e in batch], dtype=torch.int64)
    return src.to(device, non_blocking=True), tgt.to(device, non_blocking=True)
```

成立的前提是 **`tokenize` 保证长度恒为 52**，所以不需要 pad/collate。`non_blocking=True` 要配合 `pin_memory=True` 才有意义，没开时退化成同步拷贝、无副作用。

配套改了 `my_dataloader.get_dataloader(..., num_workers=0, pin_memory=False)`，默认值保持原行为：

```python
loader_kw = dict(num_workers=num_workers, pin_memory=pin_memory)
if num_workers > 0:
    loader_kw.update(persistent_workers=True, prefetch_factor=4)
```

> ⚠️ `num_workers>0` 要求入口有 `if __name__ == "__main__"` 保护，否则子进程重新 import 入口模块会**再触发一次训练**。

## 四、混合精度

```python
with torch.autocast(device_type=device.type, dtype=amp_dtype, enabled=use_amp):
    y_p = model(input, target[:, :-1])
    loss = loss_function(y_p, target_flat)

Adam.zero_grad()
if use_amp:
    scaler.scale(loss).backward()
    scaler.unscale_(Adam)                      # ← 必须
else:
    loss.backward()
total_norm = nn.utils.clip_grad_norm_(model.parameters(), clip)   # ← 量真实范数
if use_amp:
    scaler.step(Adam); scaler.update()
else:
    Adam.step()
```

三个要点：**`clip` 之前必须 `unscale_`**（否则 clip 形同虚设）、**统计用的 loss 必须未缩放**、**bf16 不需要损失缩放但仍走同一条路径**（少一套分支）。详见 [显存预算与硬件取舍](./调参经验-显存预算与硬件取舍.md)。

## 五、命令行开关

不传参数就是 4090 那套默认值：

```bash
python train_增加了自动调整断点续跑版.py                     # 默认：1000万对 / B=512 / bf16 / lr=2e-4
python train_增加了自动调整断点续跑版.py --resume             # 自动挑最近一次断点续跑
python train_增加了自动调整断点续跑版.py --resume --epochs 60  # 接着多练
python train_增加了自动调整断点续跑版.py --fresh              # 忽略断点从头来
python train_增加了自动调整断点续跑版.py --batch_size 128 --lr 1e-4   # 4GB 本机
python train_增加了自动调整断点续跑版.py --max_pairs 20000 --epochs 1 # 冒烟测试
```

| 开关 | 默认 | 用途 |
|---|---|---|
| `--max_pairs` | 10,000,000 | 冒烟测试用小值 |
| `--batch_size` | 512 | 显存不够往下退 |
| `--lr` | 2e-4 | 跟 batch 成比例改 |
| `--min_count` | 3 | 词表裁剪 |
| `--num_workers` | 8 | 0 = 退回单进程 |
| `--data_path` | 脚本内写死 | 换语料 / 本机冒烟 |
| `--amp/--no-amp` | 开 | 排查数值问题 |

> 顺带修了原文件的一个"文档承诺但没实现"：开头用法示例写着 `--max_pairs 2000 --epoch 2`，但这两个参数一个都没注册，照着敲只会 `unrecognized arguments`。现在补上了（并且示例里的 `--epoch` 改成实际的 `--epochs`）。

## 六、验证方法：10 组断言

`my_/手动复现/断点续跑自检.py` 做的是**对照实验**，不是"看着像对"：

| 段 | 验什么 | 判据 |
|---|---|---|
| A/B | **一次跑完 5 轮** vs **跑 3 轮→续跑 2 轮** | 逐轮 `[epoch N] 汇总` 输出**逐字一致**；最终权重最大差异 = 0 |
| — | 断点写入的轮数与状态 | 跑满计划轮数 = `finished`，中途进程死掉 = `interrupted` |
| — | 参数解析 | `--resume` 不带值 / 带目录 / `--log_dir` / `--fresh` |
| C | 配置对不上时必须报警 | 换 `src_vocab_size` 后必须打印"对不上"，**且没轮次可跑时也要报** |
| C2 | 续跑不能把 best 指标搞坏 | `best_val_acc` 只增不减 |
| D | 断点字段完整性 | 11 个关键字段齐全；`meta` 里的配置不能是 `None` |
| E | lr / 调度器耐心计数 / best 确实被恢复 | 与断点里记的值逐项相等（手写一个假 lr，验它被断点值纠正） |
| F | 原子写 | 手写一个半截 `.tmp`，正式断点仍可读 |
| **H** | 从旧版格式断点续跑 | 只认 `best_resnet18_9.pth` 的老目录也能接上；`-inf` 兜底后第一轮恢复正常 |
| **I** | 混合精度路径 | CPU 上 bf16 跑通，loss/acc 与 fp32 **逐字一致**（证明统计没被缩放污染） |
| **J** | 向量化拼装 | 与逐样本拼装结果**逐元素相同**、dtype/形状一致 |

跑法（用 240 条假数据 + 迷你模型，秒级完成）：

```bash
python my_/手动复现/断点续跑自检.py
```

> 为什么用迷你模型：真模型 120M 参数 + 5.9GB 语料跑不动。但**逐字一致**这条断言对模型大小不敏感——只要漏了 `rng_state`（shuffle 顺序）、`scheduler_state`（耐心计数）这类东西，第 4、5 轮的 loss 立刻就对不上。

### 自检抓出的三个真 bug

这是"写验证脚本"最实际的回报：

| # | Bug | 怎么暴露的 |
|---|---|---|
| 1 | `_save_state` 读的是模块级 `CONFIG`，而不是 `train()` 收到的 `config` | 自检传了 `config`，断点里 `meta` 全是 `None` → 配置核对形同虚设 |
| 2 | `--resume` 只扫**脚本目录**，而日志目录是相对路径落在 **cwd** | 冒烟测试时日志在仓库根、脚本在子目录，`--resume` 一路报"没找到断点" |
| 3 | "没有可跑轮次"时的提前返回，顺手跳过了配置检查 | C 段断言直接失败 |

第 2 个尤其典型：**只有真的从另一个目录跑一次才会暴露**，读代码看不出来。

## 七、上线验证清单

```bash
# 1) 冒烟（2 分钟）：确认改动没破坏形状/流程
python train_增加了自动调整断点续跑版.py --max_pairs 20000 --epochs 1 --fresh

# 2) 正式（默认 1000 万对）
python train_增加了自动调整断点续跑版.py --fresh

# 3) 断了就接
python train_增加了自动调整断点续跑版.py --resume
```

第一轮要盯的三个数：

| 看什么 | 期望 | 不对怎么办 |
|---|---|---|
| `[time] 本轮用时` | 明显低于旧配置外推的 90 分钟 | 还是 90 分钟 → `num_workers` 没起作用，回来排查 |
| `Grad/norm` 曲线 | 与旧训练同量级 | 持续 >10 → `--lr 1e-4` 重跑 |
| `Loss/valid_epoch` 与 `Acc/valid_epoch` 的张口 | 比 43.7% vs 33.7% 明显收窄 | 没收窄 → `max_pairs` 还得往上加 |

最终验收看 **valid BLEU**，参照 `results/bleu.txt` 里的 29.26。

## 八、遗留项

1. **1000 万对规模没跑过**：本机只有 400 行迷你语料。建词表 + tokenize 预计 **5~15 分钟、峰值内存约 8GB**（按 100 万对实测"准备 50s"外推）。
2. **`num_workers>0` 没验证**：沙箱禁止命名管道，多进程 DataLoader 直接 `WinError 5`。
3. **拼装还没挪进 worker**：现在子进程传的是 dict 列表，还要过一遍进程间 pickle。让 collate 在子进程直接产出整块张量是数据管道剩下最大的一块。
4. **本轮改动只提交未推送**：`git log origin/main..HEAD` 可以看到待推送的提交。
