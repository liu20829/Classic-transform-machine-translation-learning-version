# 显存预算与硬件取舍

> 一句话：显存的大头不是模型参数而是输出层 logits（单这一个张量就 2.84GB），把 4GB 和 24GB 当成"两套参数"而不是"一套调大调小"；24GB 上真正的瓶颈会从显存转移到 CPU 侧数据供给。
> 关键词：logits 显存, 混合精度, bf16 vs fp16, DataLoader 瓶颈, num_workers, batch 缩放
> 生成日期：2026-09-30
> 上游问题：③「我本机是 4GB 显存，但服务器有 24GB 4090」
> 上游文档：[参数量与过拟合的真实来源](./调参经验-参数量与过拟合的真实来源.md)（给出参数量）
> 下游文档：[代码改动与验证方法](./调参经验-代码改动与验证方法.md)（本篇的参数落到代码里）

## 起点：换显卡换掉的不只是显存上限

本机 4GB、服务器 24GB。直觉是"同一套参数在服务器上放大"，但真正的差别是**瓶颈换了位置**：

- 4GB：显存不够 → 必须砍 batch、开混合精度；
- 24GB：显存富裕 → 卡在 CPU 侧的数据供给上，显卡大面积闲置。

如果不区分这两件事，就会出现"买了 4090 但训练时间几乎没变"的结果。

## 一、先把显存账算清：大头是 logits

训练时的显存有两大块，**很多人只算第一块**：

| 块 | 内容 | 大小 |
|---|---|---|
| ① 模型自身 | 参数 + 梯度 + AdamW 的两个动量（每份 4 字节 → 参数量的 16 倍） | 按参数量算 |
| ② **激活与中间张量** | 最大的一项是解码器输出 `y_p`，形状 `(B, L, V_tgt)` | **往往是 ① 的好几倍** |

`y_p` 为什么这么大：它是"每个位置对**整个词表**打分"的结果，`V_tgt=119110` 是个十几万的数。而且它是 fp32 张量，反向还要再存梯度。

按 `B=128, L=50, V=119110, fp32`：

```
128 × 50 × 119110 × 4 字节 ≈ 3.05 GB      ← 单这一个张量
```

不同组合下这一个张量的大小：

| V_tgt | B | L | fp32 | bf16/fp16 |
|---|---|---|---|---|
| 119,110 | 128 | 50 | **2.84 GB** | 1.42 GB |
| 119,110 | 128 | 40 | 2.27 GB | 1.14 GB |
| 119,110 | 64 | 50 | 1.42 GB | 0.71 GB |
| 119,110 | 32 | 50 | 0.71 GB | 0.36 GB |
| **79,000** | **512** | **50** | **7.21 GB** | **3.60 GB** |
| 79,000 | 256 | 50 | 3.61 GB | 1.80 GB |
| 79,000 | 128 | 50 | 1.80 GB | 0.90 GB |

模型自身（含梯度与两个动量）：

| 配置 | 参数量 | 占用 |
|---|---|---|
| 原始（min_count=2，无 tying） | 120.46 M | 1,838 MB |
| + weight tying | 89.85 M | 1,371 MB |
| + tying + min_count=3 | 61.26 M | **935 MB** |

**看懂这两张表，硬件决策就出来了**：模型自身只占 0.9~1.8GB，而 logits 在 4GB 卡上单独就能吃掉 71%。**决定能开多大 batch 的不是模型大小，是 `V_tgt`。**

> 这也解释了为什么"缩层数"对显存几乎没帮助：层数影响的是 ①（已经只有 1GB 出头），而爆显存的是 ②。

## 二、两套参数

### 4GB 本机（能跑，但要克制）

| 参数 | 值 | 理由 |
|---|---|---|
| `max_pairs` | 1,000,000 ~ 2,000,000 | 显存不限制这个，但本机跑不快 |
| `batch_size` | 128（OOM 就 96/64） | logits 1.80GB + 模型 0.93GB ≈ 2.7GB |
| 混合精度 | **必须开** | 不开的话 logits 1.80GB 起步，反向再翻倍就爆 |
| `num_workers` | 4 | 本机 CPU 核数一般不多 |
| 其余 | 同服务器 | `min_count=3`、tying 与显存无关，都该做 |

### 24GB 4090（推荐配置）

| 参数 | 值 | 理由 |
|---|---|---|
| `max_pairs` | **10,000,000** | token/参数 = 2.96，且时间可控 |
| `batch_size` | **512** | logits fp32 7.21GB → bf16 3.60GB，加模型 0.93GB ≈ 4.5GB，占 24GB 的 19% |
| 混合精度 | bf16 | 显存减半 + 矩阵乘加速；Ada 架构原生支持 |
| `num_workers` | 8 | 这是 4090 上最关键的开关（见第四节） |
| `pin_memory` | True | 配合异步 H2D 拷贝 |
| `lr` | 2e-4 | batch 128→512 是 4 倍，线性缩放该到 4e-4，折中取 2e-4 |

**显存余量还很大**（4.5GB / 24GB），所以还有两个方向可选：

- `--batch_size 1024`：logits bf16 约 7.2GB，总计约 8GB，仍只占 1/3。此时 `lr` 该提到 3e-4~4e-4；
- 不动 batch，改成加数据（`max_pairs=15000000`），因为 token/参数比才 2.96，离 ≥5 还有空间。

## 三、bf16 还是 fp16

| | bf16 | fp16 |
|---|---|---|
| 动态范围 | 与 fp32 相同（8 位指数） | 窄（5 位指数），**会下溢** |
| 需要损失缩放 | **不需要** | 需要 `GradScaler` |
| 支持硬件 | Ampere 及以后（4090 是 Ada ✅） | 几乎所有现代卡 |
| 显存 | 减半 | 减半 |

脚本里的选择逻辑：

```python
amp_dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
```

4090 上走 bf16 分支，**不需要损失缩放**。但代码仍统一走 `GradScaler` 路径（`enabled=False`），理由：少一套分支就少一处出错的地方；未来换卡时不用改代码。

### 一个容易写错的地方：clip 之前必须 unscale

```python
scaler.scale(loss).backward()
scaler.unscale_(Adam)                      # ← 少了这行，下面这句就是错的
total_norm = nn.utils.clip_grad_norm_(model.parameters(), clip)
scaler.step(Adam); scaler.update()
```

`clip_grad_norm_` 量的是**真实梯度范数**。带着缩放系数去裁（fp16 下 loss 可能被放大 65536 倍），`clip=1.0` 就形同虚设——所有梯度都会被裁成缩放的 1.0，等于没裁。

还有一处：**统计用的 loss 必须是未缩放的**，否则 loss 曲线会随缩放系数的动态调整而漂移。

> 验证方式见 [代码改动与验证方法](./调参经验-代码改动与验证方法.md) 的"I"段：在 CPU 上用 bf16 跑，逐轮 loss/acc 与 fp32 **逐字一致**，说明统计口径没被污染。

## 四、24GB 上真正的瓶颈：CPU 数据供给

这是本篇最重要的一节。

### 证据来自脚本自己的注释

> "batch 20 → 128：batch 20 时每 batch 耗时（约 0.09s）和 128 一样，说明瓶颈在 **CPU 侧的 tensor 拼装**、GPU 闲着，吞吐差 6.4 倍"

**每步耗时与 batch 大小无关**，这是典型的"固定开销主导"特征。拆解一下（batch=128 时 0.087s）：

```
0.087s/step ≈ 0.05s（CPU 拼 tensor 的固定开销）+ 0.037s（GPU 计算）
```

换到 4090，GPU 那部分缩小十几倍（0.037s → 约 0.002s），但 **0.05s 的 CPU 开销一点没变**：

| batch | 每步耗时（估计） | GPU 利用率（粗估） |
|---|---|---|
| 128 | 0.052s | ~4% |
| 512 | 0.058s | ~11% |
| 1024 | 0.064s | ~23% |

**也就是说：换 4090 之后，如果不修数据供给，显卡大部分时间在等 CPU。**

### 三个修法，按性价比排序

**① `num_workers` 打开（最大的一笔，改动最小）**

原来 `DataLoader(...)` 没传 `num_workers`，默认是 **0** —— 取数据和拼 tensor 全在主进程串行做。

```python
loader_kw = dict(num_workers=num_workers, pin_memory=pin_memory)
if num_workers > 0:
    loader_kw.update(persistent_workers=True, prefetch_factor=4)
```

- `persistent_workers=True`：epoch 之间不销毁子进程，省掉每轮重新 fork；
- ⚠️ `num_workers>0` 要求入口脚本有 `if __name__ == "__main__"` 保护，否则子进程会重新 import 入口模块、**再触发一次训练**（Windows 上必崩）。

**② batch 拼装向量化**

原来一个 batch 要做 128 次 Python 迭代 + 128 次 `torch.tensor`：

```python
# 旧：逐样本建张量再 cat
for example in batch:
    input.append(torch.unsqueeze(torch.tensor(example.get("src")).type(torch.int64), dim=0))
input = torch.cat(input, dim=0).to(device)

# 新：一次出整块
src = torch.tensor([e['src'] for e in batch], dtype=torch.int64)
```

**为什么可以直接这么写**：`my_tokenizer.tokenize` 保证每句长度恒为 `max_sent_len + 2 = 52`（不足补 PAD、超长截断），所以**本来就不需要 pad/collate**，也就没理由一个样本一个样本地单独建张量。

> 验证：与逐样本拼装的结果**逐元素相同**（见 [代码改动与验证方法](./调参经验-代码改动与验证方法.md) 的"J"段）。

**③ 把拼装挪进 worker（还没做）**

现在 `collate=lambda x: x`，子进程把 dict 列表 pickle 过来，主进程再拼。如果让 collate 在子进程里直接产出整块张量，能再省一截进程间传输。这是数据管道剩下最大的一块，**本轮没做**。

### 反过来，什么时候才轮到加显存

如果做完 ①②③ 发现 `[time] 本轮用时` 明显下降、GPU 利用率上来了，那时才轮到"加 batch / 加数据 / 加模型维度"。在这一步之前加显存预算都是浪费。

## 五、时间账（含"必须实测"的提醒）

按旧配置（B=128、单进程、fp32）外推：

| `max_pairs` | 分钟/轮 | 30 轮 | 早停（约 20 轮） |
|---|---|---|---|
| 100 万 | 9.1 | 4.5 h | 3.0 h |
| 200 万 | 18.1 | 9.1 h | 6.0 h |
| 500 万 | 45.3 | 22.6 h | 15.1 h |
| **1000 万** | **90.6** | **45.3 h** | **30.2 h** |

> ⚠️ **这张表不能直接拿来规划 4090 上的时间。** 它是用"0.087 s/batch"直推的，而那个数字本来就是 CPU 瓶颈下的值。修完数据供给后应该会快很多，快多少必须实测。
>
> 所以上线后第一件事不是看 loss，而是看 `[time] 本轮用时`。

关于 1000 万对是否"太久"：30 小时看着吓人，但**早停在 8 轮不提升时就接走**，而且断点续跑可以随时停随时接——不需要一次性留出 30 小时（见 [代码改动与验证方法](./调参经验-代码改动与验证方法.md)）。

## 六、本篇的结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | 显存大头是输出层 logits，不是模型参数 | 2.84GB vs 935MB |
| 2 | 决定 batch 上限的是 `V_tgt`，所以砍词表同时也在省显存 | logits 表 |
| 3 | 4GB 必须开混合精度；24GB 开 bf16 只要 4.5GB | 两套参数表 |
| 4 | 24GB 上的瓶颈是 CPU 数据供给，不是显存 | 每步耗时与 batch 无关 |
| 5 | `clip` 之前必须 `unscale_`，否则 clip 形同虚设 | GradScaler 用法 |
| 6 | 时间必须实测，旧的外推值不可用 | 0.087s 本身是瓶颈值 |

## 未验证项

1. **`num_workers>0` 本机测不了**：沙箱禁止命名管道，多进程 DataLoader 直接 `PermissionError: [WinError 5]`。上线后要看 `[time] 本轮用时` 是否真的下降。
2. **4090 上的实际每步耗时未知**：上表是外推，不是实测。
3. **GPU 利用率是粗估**：按"固定 0.05s + 计算时间线性缩放"推的，实际还受 kernel 启动开销、CPU 频率等影响。
