## 跨文档的三条主线

### 主线一：先测量，再调参

这一轮真正的转折点是**没有直接调超参**。原计划的思路是"过拟合了 → 调 dropout / 加正则 / 缩模型"，量完之后发现方向全错：

- `dropout=0.15` 在正常范围，问题不在它；
- 缩模型没用，因为主体只占 10.7% 的参数（见第二篇）；
- 唯一真正治过拟合的旋钮是 `max_pairs`，而它被卡在 100 万。

**沉淀成规则**：过拟合时先算 token/参数比，再决定是"加数据"还是"减参数"。比值 ≥1 之前，加正则都是隔靴搔痒。

### 主线二：参数在哪，优化就该在哪

| 观察 | 推论 |
|---|---|
| 嵌入+输出占 89.3% 参数 | 砍层数省不了多少，砍词表立竿见影 |
| 输出层和目标嵌入形状完全相同 | weight tying 白赚 25% 参数，精度代价 0 |
| 只出现 1~2 次的词占词表一多半、只贡献不到 1% token | `min_count` 2→3 用 1 个点的 UNK 换掉一半词表 |

### 主线三：硬件换了，瓶颈也换了

4GB 本机和 24GB 4090 不是"同一套参数调大调小"，而是**两个不同的瓶颈**：

- 4GB：显存不够 → 必须开混合精度、batch 往下退；
- 24GB：显存富裕 → 瓶颈转移到 CPU 侧数据供给，脚本里自己测过"batch 20 和 128 每步耗时一样"，那就是证据。

所以第三篇给的不是一套参数，而是**两套**，以及判断该用哪套的依据。

## 遗留与未验证项（写清楚，别当成已验证）

1. **1000 万对规模没跑过**：本机只有 400 行迷你语料，建词表 + tokenize 的耗时和峰值内存是按 100 万对实测（准备 50s）外推的。
2. **`num_workers>0` 没验证**：沙箱禁止命名管道，多进程 DataLoader 直接 `WinError 5`。上服务器后要看 `[time] 本轮用时` 有没有真的下降。
3. **`lr=2e-4` 是折中值**：batch 128→512 按线性缩放该到 4e-4，但这个模型对 lr 敏感（有 lr 被砍到 6.25e-6 后空转 60 轮的记录），取 2e-4 保守起步，要看 `Grad/norm` 曲线决定是否上调。
4. **只提交未推送**：截至本文档生成时，本地领先 `origin/main` 若干提交（`git log origin/main..HEAD` 可查），尚未 push。

## 数据来源分三档（读的时候注意区分）

| 档 | 含义 | 例子 |
|---|---|---|
| **实测** | 本机直接量出来的 | 句长分布、丢弃率、词频、参数量、断点字段验证 |
| **实测+外推** | 采样或小规模实测后按比例放大 | 2475 万对的总 token 数 |
| **推算** | 按公式或他人实测值算的 | 显存占用、时间账 |

**推算的部分上线后要用实测替换**，尤其时间账——它取自 CPU 瓶颈状态下的 `0.087 s/batch`，不能用来规划 4090 上的耗时。各篇正文里对应的数字都标了这个档位。
